# 商业化差距评估（2026-10-14，基于当日全量测试与代码实证）

> 回答的问题：这个项目是"可商业化、商业标准"，还是"大号玩具"？
> 一句话结论：**不是玩具——工程底子与产品完成度已达到内部质量标准的商业水准；但按"可商业化"的严格定义，当前是一个高质量的可商业化候选原型（pre-pilot），与商业标准之间隔着三条硬门槛与一组运营配套，全部可列举、可执行。**

## 二、三条硬门槛（不可绕过，逐条实证）

1. **无交易闭环**：全仓无任何支付代码（grep 实证）。当前"点餐完成"= 厨房开始准备，钱在店堂线下结。商业餐饮系统的硬要求：聚合支付（微信/支付宝）、退款、对账、支付对账差异处理。**没有支付，就只能是店内辅助工具，无法收取线上溢价。**
2. **数据不真实**：项目自述"未上线，数据库全部测试数据"；评分默认 3.5、2004 条反馈为测试数据、ML 在模拟数据上训练——R²=0.9443 是模拟数据上的拟合度，**不代表真实预测力**。商业化的推荐价值需要真实反馈飞轮验证。
3. **部署形态是开发态**：本机 Windows + pm2 + cloudflared 临时隧道。无云主机、无域名证书、无数据库托管、备份仅本机每日一份、无异地容灾。**一次断电/故障 = 服务中断，无 SLA 概念。**

## 三、商业化配套差距（按优先级）

**M1 单店试点前必须（约等于"敢让真实顾客用"）**：
- [ ] 云部署 + 域名 + HTTPS（替换临时隧道）
- [ ] 主动告警（worker 挂/错误率/磁盘——现为 grep 实证无任何通知渠道，全靠人看面板）
- [ ] 并发压测（现有 performance_benchmark 仅单请求延迟基准，并发容量未知；单进程 Node + 内存限流桶的容量天花板需要数字）
- [ ] 实拍图全覆盖（品牌红线：AI 图仅装饰位；已有实拍需求清单）
- [ ] 合规文本落地：用户协议 + PIPL 个人信息处理告知 + 食品经营许可展示
- [ ] 真实菜单与真实价格录入，测试数据清洗（cleanup 脚本已有）

**M2 商业闭环（"可收费"）**：
- [ ] 支付集成 + 退款 + 对账
- [ ] 找回密码自助化（现依赖店主线下核实——系统无邮箱/手机通道；商业标准需 OTP 或第三方登录）
- [ ] CI/CD 流水线（测试全在本地手工跑）

**M3 规模化（"可复制"）**：
- [ ] 多门店/多租户架构（现为单店单实例）
- [ ] 数据库托管 + 异地备份
- [ ] SLA 与运维值守

## 四、结论

用一句话分级：**工程治理与产品完成度 = 商业标准；数据与部署 = 演示级；交易与规模化 = 未开始。** 它不是大号玩具——玩具没有 289 条门禁、没有监察清单、没有降级链和审计债清偿机制。但它也还不是商业产品——商业产品的定义是"真实用户在真实环境为真实交易付钱"，目前三条都还是零。

好消息是：差距全部是**工程与运营工作量**，不存在架构性死结（单体架构支撑单店试点绰绰有余，多租户可在验证后重构）。按 M1→M2→M3 推进，每一步都有明确的验收清单。
