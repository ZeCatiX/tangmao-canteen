# 审查报告 · 结算与会话绑定状态机（2026-10-16）

> 起因: 全量 GUI 测试（2026-10-15 晚）G8 组发现订单 12883 被静默变异（13 桌→打包、购物车并入），判定此类"结算/桌号/会话绑定"问题此前未被彻查。本文通读前端 core.js 结算链路 + 后端 orders.js 三入口后逐场景判定，含实测证据。
> 结论一句话: **同桌加菜/换桌主干逻辑健康；一个 P2 级 UX 洞（选桌器静默挪单）+ 一个 P3 级加固缺口（服务端桌号零格式校验）**，其余为设计语义确认与低概率备注。

---

## 一、状态机地图

### 前端（js/core.js + js/init.js）

绑定状态全部在 **sessionStorage**（随标签页生命周期）:

| 键 | 含义 |
|---|---|
| `lockedTable` | 当前锁定桌号（选桌后锁定，购物车/偏好页只读展示） |
| `lastOrderId` | 本会话绑定进行中订单 id |
| `lastOrderTable` | 绑定订单的桌号（跟随挪桌同步） |
| `lastOrderItems/Rounds/AI/Stats` | 账单时间线与统计（展示用） |
| `sideOrder`/`orderBackup` | 赠菜模式临时态（给别桌加菜） |

两条关键判定:

1. **加菜 vs 新单**（checkoutCart, core.js≈2886）:
   `isAddMore = lastOrderId > 0 && lastOrderTable === tableNumber`
   → 加菜走 `POST /api/order/:id/add`，否则走 `POST /api/order` 新建。
2. **选桌即挪单**（applyTableChoice, core.js≈2426）:
   选桌器任何选择（30 个快捷钮/输入确认/🥡打包带走）都进入此函数——
   **若存在绑定订单且新桌号 ≠ 当前桌号，直接 `PATCH /api/order/:id/table` 把进行中订单整体改桌**（含改成"打包"），随后 `lastOrderTable` 同步为新值。
   `intent==='checkout'` 时选完自动续结算 → 因 `lastOrderTable` 已更新，购物车**并入被挪的单**。
   `init.js:906`: 🥡打包带走按钮 = `applyTableChoice('打包')`，无条件走同一逻辑。

### 后端（server/routes/orders.js）

| 入口 | 校验 | 缺口 |
|---|---|---|
| `POST /api/order` | 起售量/服务端重算/售罄/10 秒幂等(全 PG 侧)/防刷(桌→用户→IP 三级) | **tableNumber 零格式校验**（任意字符串直插库） |
| `POST /api/order/:id/add` | 归属三选一(本人/管理员/同桌凭证)+状态闸(completed/cancelled 拒)+复合键合并+起售量合并口径 | 同上（body 的 tableNumber 仅用于授权回退） |
| `PATCH /api/order/:id/table` | 归属三选一+状态闸 | **tableNumber 零格式校验** |

对照: `recommend.js` 的 parseTableParams **有** `^\d{1,2}$|打包` 校验——同一仓库两套口径。

## 二、发现清单（按严重度）

### F1 · P2 · 选桌器静默挪单（含"打包"改写）

- **复现（真实用户路径，无需任何测试工具）**: 顾客在 12 桌有进行中订单 → 购物车点「更换桌号」（或偏好页桌号输入）→ 选桌器弹出 → 点「🥡 打包带走」（或任一桌号钮）→ **进行中订单整体改为打包/他桌，无任何确认或提示**；若从"去结算"进入（intent=checkout），购物车还会并入该单。
- **实测证据**: 全量测试 G7-G9，订单 12883（12 桌建单 49 元 → 挪 13 桌 → 打包带走后变打包 79 元，两轮购物车静默并入）。
- **根因**: applyTableChoice 把"为下一单选桌"和"挪当前订单"两个意图合并成一个动作，且对"存在绑定订单"这一事实零提示。设计语义本为"订单跟客人走"（换桌防呆 2026-10-12 验证过），但打包按钮的文案语义是"新建外带单"，两意冲突。
- **建议**: ①检测到绑定订单时，选桌器顶部显示提示条"当前订单 #N 在 X 桌，选择将把订单改至 Y"并要求确认（一次性，不打扰普通换桌）；②🥡打包带走文案在有绑定订单时改为"转为打包"；③或拆分意图: 有进行中订单时打包钮 = 新建外带单（更符合直觉）。

### F2 · P3 · 服务端桌号零格式校验

- **实测**: `POST /api/order` 带 `tableNumber:'X99乱码'` → 200 建单成功；`PATCH /table` 改成 `另一个乱桌号` → 200 成功（同桌凭证匹配乱码自身即通过）。
- **佐证**: 库内历史脏数据 `ET936320C`/`KT935892` 等（测试脚本残留）即由此进入。
- **影响**: 前端是唯一防线；任何脚本/异常客户端可污染桌号维度（桌码账单、厨房按桌聚合、日报口径）。不上线前风险低，上线前应补。
- **建议**: orders.js create/move 补 `^\d{1,2}$|^打包$` 校验（对齐 recommend.js），非 400；可选做一次性清洗迁移。

### F3 · P3 · "不能加菜"不自动回退新单 ✅ 已修复（2026-10-16，用户实测撞车后落地）

- 场景: 会话绑定的订单被厨房完成后，顾客再结算 → `/add` 400 → 前端清掉全部绑定（好，下次能新单）**但当前这次结算直接报"加菜失败：订单已完成"**，购物车保留，需用户再点一次结算。
- **修复（已落地）**: checkoutCart 失败分支捕获"不能加菜"与"订单不存在或无权操作"(isAddMore 时) → 清绑定并自动以新单重试一次（幂等闸防重复），toast "上一单已结束，已为你新建订单 #N"。回归: tests/order_status_check.test.js。
- **附带收尾**: 同日新增 GET /api/order/:id/status-check 订单存活校验端点（授权与 /add 同口径），购物车"正在加菜"横幅渲染时异步自查——订单已完结/取消/失同步即清绑定收横幅，杜绝"对死订单宣称正在加菜"的误导展示（用户实测复现过）。回归同文件。
- **建议**: ~~捕获该错误后自动以新单重试一次~~（已实现）。

### F4 · 备注 · 关标签重开=同桌双单

- sessionStorage 绑定随标签关闭消失；顾客中途关页重扫桌码 → 新会话新单，同桌出现两张进行中单。桌码账单页按桌聚合展示（最近 20 张非取消），展示层已兜底；厨房看板会看到两卡。属无登录体系下的固有边界，不建议改。

### F5 · 备注 · 跨设备挪桌可造成会话失同步

- 绑定状态是纯前端会话态；顾客用两台设备时，A 设备挪桌后 B 设备的 `lastOrderTable` 仍是旧值 → B 加菜时同桌凭证不匹配 → 404（安全侧正确），但用户侧表现为"加菜失败"。低概率，登记备查。

## 三、设计语义确认（勿当缺陷"修复"）

1. **同桌凭证授权**: 游客知道别桌 orderId + 正确桌号即可加菜——"桌号即凭证"是既定设计（免登录体系下最优解）。
2. **一会话一张进行中账单**: 所有加点自动并入绑定订单，是"扫码点餐=一个顾客一顿饭"的连贯模型，主干健康。
3. **换桌=订单跟人走**: 状态闸（completed/cancelled 拒绝）+ 归属三选一均已验证。
4. **幂等与防刷**: 10 秒 PG 侧幂等、桌→用户→IP 三级频控、双结算 disabled——均在前几轮修固，本轮无回归。
